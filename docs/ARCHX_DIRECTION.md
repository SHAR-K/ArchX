# ArchX 方向：面向 Agent 的架构开发

> 更新时间：2026-09-09
> 状态：已确认的方向与第一阶段范围。它取代此前「画布 + 节点 + 提案」那一代的产品定位。

## 1. 变了什么

**旧的**：人先在画布上画目标架构，声明节点、契约、所有权，Agent 在节点范围内写代码，门禁校验
实现有没有偏离画布。对象是分区、节点、提案、审批；入口是「你的目标架构」；代码事实只是对照用的
旁证，所以界面只读七个 schema 1 字段也够用。

**新的**：**面向 Agent 开发**。引擎扫出代码事实，工具做确定性派生，Agent 拿到这份分析、把它拆开，
据此进行约束开发。图表是画给人看的，用于理解和审核，不是干活的地方。人的入口是跟 Agent 说话。

这不是换一种画法，是底下的对象模型换了：从「分区 / 节点 / 提案」换成「事实 / 派生 / 声明」。
所以插件界面重写，而不是改造。

两个容易搞混的说法，这里说死：

- 不是「基础分析无需 AI」。那等于把工具退回成人在界面上干活。分析是给 Agent 用的。
- 不是「把 HTML 原型整页搬进 webview」。只借鉴各页的分析表达方式，按插件的形态重新组织。

## 2. 数据只有一条路，两个出口

```
引擎（ArchCheck）
   → 事实 partition.json
   → 投影 packages/facts-view/src/projection.mjs
   → 按主题派生 packages/facts-view/src/<主题>/
        ├── MCP：结构化结果给 Agent，可按主题、按对象、按字段路径切片
        └── Webview：同一份结果画给人看
```

两个出口共用同一个快照 ID 和同一批对象。人在图上看到的和 Agent 说的必然是同一件事，审核才成立。

派生只出普通数据结构，布局只出坐标，不出 SVG 字符串。渲染由消费方各自实现。

## 3. 稳定 ID 是 Agent 和人之间唯一的共同指针

Agent 说「这条反向边」「这个单元」「这个状态」，人要能在界面上定位到同一个东西；人点中一个东西，
要能复制出一个引用丢回给 Agent。所以每个派生对象都要有稳定 ID：

- MCP 的返回里带 ID
- 界面能按 ID 选中并高亮
- 界面上任何对象都能复制它的 ID

这一条在第一阶段就要定死，之后再改代价很大。

## 4. 主题

数据按主题组织，不按数据类型，也不照搬原型的页签数量。每个主题回答一个问题。

| 主题 | 用户问题 | 数据 | 无数据时 |
| --- | --- | --- | --- |
| 执行关系 | 从哪里开始，什么会被触达 | 入口、调用与注册关系、可达性、证据 | 区分「没有已知入口」和「没取到调用事实」 |
| 依赖 | 谁依赖谁，具体依赖什么 | 单元与目录关系、关系类型、聚合依据、源位置 | 区分「没有关系」和「只取到部分关系」 |
| 顺序与时间 | 先后关系、等待点和周期 | 控制流、让出与等待、时间来源及置信度 | 不从调用顺序推断真实耗时 |
| 共享与并发 | 哪些执行单元访问同一资源 | 读写、执行域、保护证据、冲突候选 | 不把未识别的保护当作一定无保护 |
| 状态转换 | 状态如何变化，条件在哪里 | 状态、转换、条件、来源 | 区分「未发现」和「不支持识别」 |
| 内存占用 | 空间花在哪，基于哪个产物 | 链接产物、符号与对象占用、产物新旧 | 无产物时明确不可分析 |

所有主题共用同一套交互契约：选择、筛选、查看证据、代码定位、复制稳定引用。布局和交互状态不写回
正式架构，也不写回代码事实。

## 5. 第一阶段的工作流

```
人：调用 archx:archcheck
  → Agent 跑引擎，拿到代码事实
  → 派生出各主题的视图数据
  → 通知插件显示
  → Agent 把关键读数讲给人
人：在插件里核对，点对象看证据、跳代码
```

插件在这一阶段是显示面和审核面，不是工作台。扫描按钮可以留作便利，但不是主路径。

### 通道

宿主与 MCP 之间已有一条单向文件通道：宿主写状态到
`%LOCALAPPDATA%\ArchX\native-context\<projectKey>.json`，MCP 读。

反向那条按对称做法：MCP 写视图请求文件，宿主用文件监听接收并切换显示。不用本地端口，不触发防火墙，
和现有模式一致。请求里带快照 ID，宿主据此判断请求指的是不是当前这份事实。

### MCP 表面要换

现有 11 个工具全部围绕旧模型：节点契约、已批准任务、变更请求、开始执行、验证、完成。新的表面是
事实查询加视图控制：

- 按主题取派生结果
- 按对象 ID 取详情
- 按字段路径取切片，带 offset / limit

Agent 的上下文有限，几 MB 的事实不能整吞，「把分析拆开」这件事要靠接口支持。

### Skill 要换

现有 design / discuss / implement / propose / verify / deliver 都是旧流程的。第一阶段先加
`archx:archcheck`：跑引擎、派生、让插件显示、把关键读数讲给人。约束开发那几个在后面的阶段重写。

### 旧代码

界面重写，但宿主侧的 `project-store`、`gates`、`execution-store` 保留，第一阶段不接界面。约束开发
最终还要用到门禁，只是它的校验对象会从「符合画布」变成「符合声明与事实」。

## 6. 验证与边界

通用样例放 `corpus/`，第一个是 `blinky`。回归测试只用自建样例，不依赖 clangd，也不依赖任何真实工程。

真实工程只做只读验收：确认渲染和读数对不对。它的源码、事实、符号、目录、参数不得进入本仓库、提交、
VSIX、文档或测试夹具，改名脱敏也不算数。验收发现问题记为「失败 / 不支持 / 数据不足」，修复要另建
独立的通用样例复现，不移植真实工程的场景。

### 表现形式：哪些补了，哪些没补

主题按问题重新归并是有意的，配色交给 VS Code 主题也是。但六个主题里有五个当初被做成了表格，
那不是取舍，是赶进度赶出来的——一个主题一次提交的节奏下，表格永远是最快出数据的形式。
对着原型逐条过了一遍，结论分三档：

| 原型里的表达 | 处置 | 理由 |
| --- | --- | --- |
| 依赖：排序回放 | 已补 | 派生层每一步都算好了，只缺渲染。React 按 key 复用节点，动画反而比原型真 |
| 依赖：切割集 | 已补 | 「要动哪几处」的清单，表格讲得清，缺的是根本没画 |
| 运行图（原型里是执行关系下的一页） | 已补，放进「共享与并发」 | 上排中断、下排线程、中间三层共享变量，写方 → 变量箭头、变量 → 读方细线，流向分五类、问题分五类，能切到单个单元的一页。它的数据就是 sharedResources，回答的是「哪些执行单元访问同一资源」，所以按问题归到并发主题，和矩阵并列——矩阵答「谁碰了什么」，图答「数据从哪产出流到哪消费」。模型在派生层，MCP 拿同一份；布局只出坐标 |
| 顺序与时间：循环次数 | 已补 | 引擎从 for 头部读出的计数（变量、起止、步长、上界来源）早就在 timing 主题输出里，MCP 读得到、界面没画。循环表加一列，措辞只说「最多」——引擎只读头部，体内改了计数器就不成立 |
| 运行模式带（原型 `renderModeStrip`） | 不单独补 | 运行图的每个节点已经带节奏文字（抢占优先级 / 周期 / 忙轮询），时间主题也有单元节奏表，再画一条带是重复 |
| 执行关系：函数搜索 → 倒推到入口 | 已补 | 原型里每页右侧都有的全局入口。搜索在 webview 本地做（函数表已在 payload 里），链按需向宿主要；原型只找第一个碰到的入口，这里列出全部能到它的入口和各自的最短链，每跳标出调用 / 注册 / 中断触发，点链让树沿着它展开。**MCP 侧还没有对应工具**——Agent 目前问不了「哪些入口能到这个函数」，待补 |
| 执行关系：双根对比 | 已补 | 派生层的 `compareRoots` 早就写完了，但没有任何消费方——和排序回放一样只差渲染。矩阵进了主题输出，Agent 和人拿的是同一份数；样例加了中断里点灯，矩阵才有格子 |
| 顺序与时间：一轮的列式展开 | 已补 | 表格说不了「先走到哪、在哪停下」，这个表达承载信息 |
| 状态机 UML | 重做 | 当初其实没完整搬：A2 那版是按 depth 分行、回退边一律往右甩 42px 的赶工图，真实工程里 9 层 4 条回退的机器会叠成一团。现在照原型用 dagre 走线（层仍由我们的 depth 钉死，它只管同层顺序和走线，回退边反着喂再倒回点序），加回初态、终态同心圆、非 case / 无入弧 / 经 helper 改写的旗、子状态机可点进去、滚轮缩放拖动平移；选中状态的出边挂编号，和侧栏里的转换条目一一对应——原型的悬浮条件框不恢复，明细在侧栏，图上只留对应关系 |
| 状态机：枚举一览 | 已补 | 状态名对到引擎给的枚举定义上，列出每个成员有没有 case、入出度、角色。「未在 switch 出现」的成员是设计和实现对不上的地方。C6 修出来的枚举值在这里第一次有了出口——之前 `enums` 进了 view 就断了 |
| 状态机：线性度判词 | 已补 | 派生层早就算了 `linearity`，MCP 里 Agent 读得到，界面上人看不到——违反 §3。现在机器头上显示百分比和判词，阈值照原型 |
| 节拍：毫秒横轴画布 | 已补，进「顺序与时间」 | 横轴 sleep 实参 × tick、纵轴任务按轮询顺序，一轮被让出点切成格，按顺序横向错开、细线回连到期时刻；上面一排时间来源芯片，下面 `dataDependencies` 表——它是这个字段唯一的消费方，C4 的「先确认消费方」有答案了。样例加了带 `scheduler_sleep(50)` 的周期任务，节拍才有节奏可测；侧栏放单元列表，选哪个看一轮在那里定 |
| 三栏外壳（顶部统计 + 画布 + 400px 常驻明细） | 改成「VS Code 侧边栏 + 舞台」 | 侧边栏视图 `archx.factsSide` 放竖排主题导航 + 本主题可选的对象（入口、状态机、中断梯子、依赖工具条）+ 检查面板；编辑区的面板只当舞台，上面只有对象本身（席克定律）。原型右侧 aside 承担的「点什么、看什么」全部落到侧栏。两个 webview 跑同一个 bundle 的两种模式，跨栏的选择状态以宿主为唯一来源（`FactsHub`），按需算的明细广播给两边；侧栏没开时舞台退回合一 |

范围内的取舍，避免又做大：

- ID 只按 `<种类>:<键>` 定这一个主题需要的两种，机器和状态；等第二个主题落地再推广成完整规则。
- 通道只传「显示这个主题」和「选中这个 ID」，不做别的。
- 不动 MCP 现有的 11 个工具，只加需要的；旧的等后面整批换。
- 不碰门禁、执行、提案。

## 8. 性能与体积：量过之后

一个中等规模的工程（两百来个文件），扫描 49.2 秒。剖面拆出四个桶，只有一个真需要多核心：

| 自身耗时 | 秒 | 性质 | 处置 |
| --- | --- | --- | --- |
| 读 clangd 管道 | 22.2 | 阻塞等待，不吃 CPU | B9，唯一的并行化场地 |
| `Path.resolve()` 13.8 万次 | 6.1 | Windows 路径系统调用 | 已修：96% 是重复的 |
| 聚簇 `total_cost` 3.2 万次 | 5.1 | 纯 CPU | 已修：幂提到循环外、整数下标 |
| `is_file()` 30.9 万次 | 4.2 | Windows 路径系统调用 | 同第二条 |

现在 38.1 秒。前三步一行并发代码都没写。

聚簇没有改成增量代价：搬一个节点会改变整个源簇和目标簇里所有边的成本项，增量累加的浮点
误差会漂，漂到某次 `new_cost >= cost` 正好卡在边界上就会得出不同的簇。自建样例守不住这种
偶发分歧。已做的两处都保证浮点逐位相同。

体积分三层，胖的是磁盘那份，不是面板：

| 层 | 改前 | 改后 |
| --- | --- | --- |
| `partition.json` 落盘 | 14.18 MB | 0.51 MB |
| 投影后的 view（只在宿主内存里） | 7.89 MB | 不变 |
| 面板 payload（真正过 postMessage） | 1.20 MB | 不变 |

14 MB 里 4.48 MB 是缩进，6.13 MB 是字符串值而其中 5.95 MB 是重复的，2.84 MB 是键名。
不缩进 + gzip 就到 0.51 MB，读还更快（61 ms → 36 ms）。

上面那组数是那个中等规模的工程。拿 332 文件 / 310 回调的 stm32h743 做静态演示页（`docs/SITE.md`）时
量到另一层：`dataDependencies` 是执行单元**两两**之间的数据依赖，O(单元²)——40383 对、169 MB，占整份
事实的 78%，而分区投影原样透传，切成四个目录也还是 169 MB。已修：分区只留一端在分区里的单元对
（→ 6.4 MB）。还没修、记在这儿的：每对平均 20 条 `resources`、每条 200 字节，消费方（节拍页）只用
`order` 和变量名；`dependencyOrder` 2.4 MB 是整工程的目录序，分区后也不裁。两条都是引擎侧的事。

**不做数据库。** 读 + parse 整份事实 61 ms，投影加建索引 16 ms，六个主题全派生 18 ms，
88 个单元的一轮全摊开 23 ms——从磁盘到全部派生完不到 120 毫秒，比任何一次数据库查询往返
都快或持平。派生只要 18 毫秒，所以派生结果也不该存，存了就要管失效。引入存储引擎是为一个
120 毫秒的问题换一个永久的复杂度。唯一立得住的场景是跨快照差分（B10），那时候要的也不是
通用数据库，是按稳定 ID 对齐的快照差分。

**不发明紧凑编码。** 对 Agent 贵的是 token 不是字节，gzip 帮不上忙，自造 DSL 更糟——它得
先花 token 学编码，还会在解码时出错。JSON 加说人话的键名对 LLM 接近最优，因为它自解释。
省 token 的唯一办法是返回得更少，那是接口形状（A14 已做），不是存储格式。

## 9. 后面的阶段

分两类：**对齐功能**是「这个工具还答不出的问题」，**体验**是「答得出但说得不好」。
功能优先。

### 途中发现、顺手修掉的

- 2026-09-24 ESP-IDF 工程恒零冲突的根因：经 `esp_intr_alloc` / `timer_isr_register` / `gpio_isr_register` 装的中断没有
  向量表，规则只能归成 callback，冲突检测取不到中断侧。`callback_register` 规则现在可声明 `context: isr`，命中的
  单元 kind 为 `isr`、带 `registeredAt` 与 `rule`、没有 `vector`。grblhal-esp32：0 → 162 个候选（24 medium）。
  `corpus/rtos-mini` 里加了一个 `gpio_isr_handler_add` 装的中断守着这条。
- 同日踩的坑：`python -m archcheck` 在本仓库 `engine/` 目录下跑，导入的是 pip -e 装的**另一个仓库**的引擎，
  两次「重扫」用的都是旧规则，读数一模一样还以为规则没命中。`tools/facts-scan.mjs` 早就显式设了
  `PYTHONPATH=engine/src`，手工跑引擎也必须这么做（或 `pip install -e ./engine` 指到本仓库）。

- 2026-09-23 打包的引擎没有规则文件。pyinstaller 构建脚本只带了 `templates/`，`profiles/*.yaml` 一直没进 exe，
  所以 VSIX 里的引擎从 09-09 起就认不出任何 RTOS——插件里所有「调度模型未知」都是它，而源码跑引擎的人永远
  看不到。教训写进了 `tools/build-archcheck-engine.ps1` 的注释和 `archcheck-engine-smoke.mjs` 的断言：
  数据文件的打包必须有一条在 exe 上跑的断言，不能靠源码测试替。另一个坑：Windows PowerShell 5.1 按 ANSI
  读无 BOM 的 .ps1，中文注释末尾的多字节字符会吞掉换行连带下一行语句，那个文件里的注释只能写 ASCII。

- `externalSymbols.declaredIn` 的 column 一直硬编码成 1，改用真实列号。
- `loops` 里会出现完全相同的两条记录（真实工程上 261 条里有 1 条重复）。稳定 ID 按「函数 +
  函数内第几个」构造，重复记录会撞 ID，所以在 `ast_facts.py` 收尾处按身份去重了。**根因没查到**：
  两条记录的函数、行、列、kind、depth、endLine 全都一样，不是同一行写了两个循环。
- 界面「复制引用」按钮生成的是 `res:<名字>`，而矩阵行的 ID 是 `res:<变量ID>`，两者对不上，
  复制出来的引用定位不回那一行。改成共用 `idOf.resource`。
- 内存主题的表格里每个数字都被画成了蓝色徽章：`.num` 既是表格「右对齐等宽数字」的列类，又是状态转换
  序号徽章的类名，A2 和 A6 各自取名时撞了。徽章改叫 `.badge-num`，表格的 `.num` 只管对齐。
- 一轮沿注册边钻进了被注册任务的循环：main 注册 heartbeat_task 之后，main 的一轮里多出一个 heartbeat
  主循环的框。注册是取函数地址装进系统，不是在这里调它，那个循环在调度器手里转。样例加了周期任务
  才照出来，`sequence.mjs` 里注册类的步骤不再追循环链。
- `runMode` 的判定依赖 `semanticEdges` 的顺序，而那个顺序依赖 ID 字符串排序——带行号的时代，
  加一行注释就可能重排边、换一条判定路径。去行号之后这个排序才稳定下来。
